## Bloquant (historique — RÉSOLU, voir "Repassage" en tête de document)

### 1. `deleteEvent()` n'a pas reçu la garde `S.penMode` — permet de créer un `PEN_GOAL`/`PEN_SAVE`/`PEN_OFF` orphelin, sans crash mais avec corruption silencieuse de données

`app.js` l.1808-1817 :
```js
function deleteEvent(idx){
  if(S.readOnly) return;
  const ev=S.events[idx]; if(!ev) return;
  const a=ACTIONS[ev.type];
  const pLabel=...
  const desc=...
  if(!safeConfirm(`Supprimer cet événement ?\n\n${desc}`)) return;
  S.events.splice(idx,1);
  R();
}
```
Aucune vérification de `S.penMode` — contrairement à `editEvent()`, sa fonction jumelle dans le même panneau feed, située littéralement 2 lignes plus bas (l.1819-1824) et corrigée pour STORY-33 P0-3. `deleteEvent()` est bindée sur le bouton `🗑` de chaque ligne du fil (`data-del-ev`, l.2011 markup / l.4267 binding), et **le panneau feed lui-même n'est jamais bloqué par `S.penMode`** : ni `.feed-panel` (l.1988, seule classe conditionnelle `is-readonly`, pas `is-pen-locked`) ni le bouton `⚡ toggle-feed` (l.1979/l.4259) qui l'ouvre.

Confirmé dans le diff : `git diff app.js` montre `deleteEvent()` uniquement comme contexte non modifié autour du hunk qui ajoute la garde à `editEvent()` — la fonction elle-même n'a reçu aucune retouche dans ce cycle. C'est donc un angle mort de la couverture P0/P1 de STORY-33, pas une régression introduite ailleurs.

**Scénario de défaillance concret :**
1. Romain obtient un PO → `PEN_OBT` enregistré en `S.events[0]`, encart pénalty ouvert (`S.penMode=true`, `S.actionPanel` porte le tireur).
2. Il ouvre le fil (`⚡`, jamais grisé pendant `S.penMode`) et tape `🗑` sur le `PEN_OBT` tout en haut (celui qui backe justement l'encart ouvert) → confirme.
3. `deleteEvent(0)` retire l'événement de `S.events` **sans toucher `S.penMode`/`S.actionPanel`** (à la différence de ce qu'aurait fait `undoLast()` sur ce même événement). L'encart reste affiché à l'identique — aucun signal visuel qu'un état incohérent vient d'être créé.
4. Il tape BUT (ou ARRÊT sans suivi GB, ou HORS CADRE) → `choosePenOutcome()` → `validateAndClose()` crée bel et bien un événement `PEN_GOAL`/`PEN_SAVE`/`PEN_OFF`, sans qu'aucune vérification n'existe sur la présence réelle du `PEN_OBT` antécédent (`validateAndClose()` ne vérifie que la validité du **joueur**, jamais celle de l'événement `PEN_OBT` d'origine).
5. Résultat : un "But Pen"/"Arrêt Pen"/"Pen HC" apparaît dans le fil sans aucun `PO` avant lui, et s'il s'agit d'un but, il compte normalement dans le score et dans les stats gardien pénalty (`gkStats()`, `!isPen` exclut les stats normales mais les compteurs `penGoals`/`penSaves`/`penTotal` l'incluent bien) — une incohérence de narration de match silencieuse, sans exception JS, exactement le type de risque que P0-1 avait pour objectif de fermer.

Le même chemin est atteignable pendant la sous-étape "grille de zone" (après `choosePenOutcome()`, avant de taper une zone) : supprimer le `PEN_OBT` via `🗑`, puis taper une zone → `clickGoalZone()` → `validateAndClose()` → même résultat.

```js

  if(S.penMode){
    safeAlert("Terminez ou fermez le pénalty en cours avant de supprimer un autre événement.");
    return;
  }
  ...
```

## Recommandé (non-bloquant)

1. **Message d'alerte de `deleteEvent()` parle de "modifier" pour une action de suppression.** Le correctif reprend mot pour mot le texte d'`editEvent()` ("Terminez ou fermez le pénalty en cours avant de **modifier** un autre événement.") plutôt qu'une variante dédiée ("...avant de **supprimer**..."). Compréhensible en contexte (l'utilisateur vient de taper `🗑`, l'intention est claire), et le choix de dupliquer le texte à l'identique plutôt que d'en maintenir deux variantes proches est défendable pour la maintenabilité. Pure formulation, aucun impact fonctionnel — à corriger seulement si Romain le remarque en usage réel.

2. **Double rendu dans le chemin d'échec de la revalidation P1-4.** `validateAndClose()` appelle `R()` elle-même en l.929 avant de `return`, alors que dans son chemin de succès elle n'appelle jamais `R()` (laissé aux appelants). Ses deux appelants concernés (`choosePenOutcome()` l.745, `clickGoalZone()` l.720) rappellent `R()` juste après sans savoir que le rendu a déjà eu lieu — un second rendu inoffensif mais évitable. Piste : que `validateAndClose()` retourne un booléen de succès/échec plutôt que d'appeler `R()` elle-même dans un seul de ses deux chemins de sortie.

3. **`S.trackGK`/le sélecteur de gardien adverse restent modifiables pendant l'encart pénalty** (boutons `onclick="S.trackGK=!S.trackGK;..."` l.1934 et `data-gk-sel` du côté adverse) — hors du périmètre des 3 risques P0 identifiés par le Risk Analyst, donc pas un défaut de conformité à cette story, mais à surveiller : `gk = S[oppTeam].gkId` est lu au moment de `validateAndClose()` (l.934), pas figé à l'ouverture de l'encart, donc changer le gardien adverse en cours d'encart change bien le gardien crédité/débité de l'issue du pénalty. Comportement cohérent avec le reste de l'app (rien n'est jamais figé à l'avance ailleurs non plus), mais mérite un test QA dédié si Romain a l'habitude de corriger le gardien en direct.

4. **Bouton "✕" vestige dans `statusHtml`** (l.1720, `onclick="S.actionPanel=null;S.selectedAction=null;S.penMode=false;R();"`) : ce code est mort pendant `S.penMode` puisque `renderMatchPanel()` retourne toujours via `renderPenaltyPanel()` avant d'atteindre `statusHtml` tant que `S.penMode` est vrai (l.1700) — le reset `S.penMode=false` inline n'a donc plus jamais d'effet utile ici. Sans risque, juste un résidu à nettoyer pour la lisibilité.
