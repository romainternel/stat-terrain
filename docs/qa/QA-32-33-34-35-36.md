## Bug trouvé

### 🟠 Majeur — Incohérence du calcul "Efficacité" entre Stats → Analyse (match en cours) et Bilan → Analyse (match archivé) pour tout match contenant un but sur pénalty

**Constat** : sur le match de test (3 buts FENIX dont 2 buts sur pénalty + 1 tir normal, 1 seul tir non-pénalty réellement tiré), les deux écrans affichent des pourcentages "Efficacité" radicalement différents pour **les mêmes événements sous-jacents** :
- **Bilan → Analyse** (`matchAnalysis(m)`, nouveau code STORY-35) : *"Efficacité FENIX **100%** vs Adversaire 100%"*.
- **Stats → Analyse du même match encore actif** (`autoAnalysis()`, code préexistant non modifié) : *"Efficacité FENIX **300%** vs Adversaire 100%"*.

**Cause identifiée par lecture de code** :
- `autoAnalysis()` (`app.js` ~2677) calcule le dénominateur via `teamStat("home","GOAL")+teamStat("home","SAVE")+teamStat("home","OFF")` — `teamStat()` fait un match **exact** sur `e.type` (`app.js` l.1057-1059), donc **exclut** `PEN_GOAL`/`PEN_SAVE`/`PEN_OFF` du dénominateur. Le numérateur (`teamScore()`, l.1054-1056) utilise lui `ACTIONS[e.type].isGoal`, qui est `true` pour `GOAL` **et** `PEN_GOAL`. Dès qu'un but sur pénalty existe, le numérateur les compte mais le dénominateur ne compte pas les tirs pénaltys correspondants → un pourcentage qui peut dépasser 100% (ici 3 buts / 1 tir non-pen = 300%).
- `matchAnalysis(m)` (`app.js` ~3282, nouveau code STORY-35) utilise `ms.home.eff` où `ms=matchStats(m)` (fonction préexistante, non modifiée) — dont le calcul interne de `eff` agrège correctement buts et tirs pénalty des deux côtés du ratio, donnant 100%.

**Pourquoi c'est pertinent pour ce cycle précisément** : STORY-32 rend la capture réelle des zones de pénalty courante et encouragée en usage normal — un but sur pénalty n'est plus un cas marginal mais un événement fréquent dans un vrai match de handball. Cette divergence entre les deux écrans "jumeaux" (le terme même employé par STORY-35 pour décrire l'intention de conception) sera donc visible dans la quasi-totalité des matchs réels comportant au moins un pénalty, pas seulement dans un scénario de test construit.

**Conséquence utilisateur** : un pourcentage d'efficacité affiché à plus de 100% dans l'écran du match en cours est immédiatement suspect pour un coach ; le fait que le même match, une fois archivé et consulté dans Bilan, affiche un nombre différent (et cohérent, celui-là) peut faire perdre confiance dans les deux chiffres à la fois plutôt qu'identifier lequel est fiable.

**Sévérité** : Majeur, pas Bloquant — aucun crash, aucune corruption de données, la fonctionnalité "Analyse" reste utilisable et le nombre affiché dans Bilan (100%) est le correct des deux. N'empêche pas la mise en production de STORY-35/36 en tant que telles (le défaut préexiste dans `autoAnalysis()`, une fonction que STORY-35 avait explicitement pour consigne de ne pas toucher — `docs/stories/STORY-35...md`, AC21).

**Recommandation** : ticket séparé pour le Developer — soit corriger `autoAnalysis()` pour dénominateur/numérateur cohérents (probablement en réutilisant `matchStats(S).home.eff` comme le fait déjà `matchAnalysis()`, ce qui unifierait les deux formules et fermerait la divergence par la racine), soit à défaut documenter la différence si elle est jugée acceptable. Recommandation transmise également au Scrum Master pour priorisation (hors scope des 5 stories de ce cycle, mais rendu visible/fréquent par elles).
