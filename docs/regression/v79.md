# Regression Guardian — passage avant mise en production v79

## Changement de cette version

Cycle STORY-32 à STORY-36, livré en un seul lot :

- **STORY-32** — Encart pénalty sur le terrain : remplace l'ancien court-circuit de `clickActionPlayer()` (branche PEN_OBT, qui validait immédiatement et empêchait `goalZone` d'être jamais capturé pour un penalty en direct) par un vrai encart qui reste ouvert à l'écran (`S.penMode`/`S.actionPanel` non-null en continu) : tireur pré-désigné, réassignable, 3 boutons BUT/ARRÊT/HORS CADRE, grille de zone 3×3 si `S.trackGK` actif, `✕ Fermer`. Nouvelle fonction `choosePenOutcome()`, `closePenPanel()`, `renderPenaltyPanel()`/`renderShotCourt()` (extraite)/`renderPenOutcomeButtons()`/`renderPenRoster()`. Couleurs `PEN_GOAL`/`PEN_SAVE`/`PEN_OFF` corrigées (`--gk-goal`/`--gk-save`/`--gk-off`, résout une régression de lisibilité déjà en prod où PEN_GOAL/PEN_SAVE partageaient la même couleur).
- **STORY-33** — 4 gardes de robustesse contre les actions concurrentes pendant que l'encart pénalty reste ouvert sur plusieurs re-rendus (fenêtre temporelle qui n'existait pas avant STORY-32) : `undoLast()` ferme proprement la transaction si l'événement annulé est le `PEN_OBT` en cours ; le toggle POSSESSION est neutralisé (`if(S.penMode) return;`) ; `editEvent()`/`deleteEvent()` refusent de démarrer avec un message explicite ; revalidation du tireur désigné contre le roster courant juste avant l'écriture finale (P1-4) ; activer le mode lecteur sur son propre appareil ferme immédiatement sa propre transaction plutôt que de la geler (P2-5, affine le comportement initial de STORY-32).
- **STORY-34** — Protection défensive de `renderGkSheet()` : la heatmap de zone et les compteurs ENCAISSÉS/ARRÊTÉS/H.CADRE sous le terrain SVG excluent désormais `ACTIONS[e.type].isPen`, pour que la capture réelle des zones de penalty (STORY-32) ne fasse pas silencieusement bouger un écran déjà validé (STORY-30). `gkStats()`/`gkStatsCombined()` (colonne PEN du détail) restent inchangés, continuent de les compter séparément.
- **STORY-35** — Onglet "🧠 Analyse" + notes coach éditables depuis Bilan pour n'importe quel match archivé : `matchAnalysis(m)`/`matchExportText(m)`/`periodScoreOfMatch(m,...)`, jumeaux scoped-match de `autoAnalysis()`/`generateExportText()`/`periodScore()`, jamais de paramètre partagé injecté dans `teamScore`/`teamStat`/`teamPoss`. `saveBilanNotes()` persiste via `dbSaveMatch(m)` avec l'objet match complet. `S.bilanMatch` re-dérivé à chaque rendu de `renderBilan()` (corrige un risque de référence obsolète après un aller-retour Matchs/Stats→Bilan).
- **STORY-36** — Raccourci "⚠️ Charger ce match & générer son PDF" (nouvel onglet PDF de Bilan) + extraction de `loadMatchAsCurrent()` (partagée avec le bouton "📂 Charger" de l'Historique) avec un **correctif de sécurité P0** : `S.currentMatchId=null` et `unsubscribeMatchEvents()` exécutés avant tout reset des données, pour empêcher qu'un canal Realtime resté actif n'écrase le vrai match en cours (affiché en direct sur un autre appareil) avec les données périmées d'un match archivé.

## Pourquoi une passe complète, pas un test de fumée

Ce lot touche le cœur du flux de saisie en direct : `clickActionPlayer()`, `validateAndClose()`, `autoValidatePending()`, `selectAction()`, `clickTeam()`, `undoLast()`, `editEvent()`, `deleteEvent()` ont **tous** été modifiés pour introduire un état transitoire (`S.penMode`/`S.actionPanel` non-null sur plusieurs re-rendus) qui n'existait pas avant ce cycle. C'est exactement le genre de changement qui peut casser silencieusement un flux voisin qui semblait sans rapport — le risque concret identifié par le Risk Analyst pour STORY-33 (undo, toggle POSSESSION, édition d'un ancien événement pendant que l'encart reste ouvert) en est la preuve. Le mode lecteur (STORY-26) a lui aussi reçu une garde supplémentaire (P2-5) qui touche `setReadOnly()`, un point d'entrée partagé par toute la surface d'écriture de l'app. Une passe complète du parcours critique était donc justifiée, pas seulement une vérification ciblée sur les nouveaux boutons.

## Méthode

Tests réels via CDP (`chrome.exe --headless=new`, profil temporaire dédié, port **9450** — libre, distinct de tous les ports déjà utilisés cette session), contre l'app servie en local sur `http://localhost:8990/index.html` (serveur de dev, non touché). Client CDP écrit à la main en Node 24 (WebSocket natif, pas de dépendance externe), viewport 1180×900 (garantit `S.mode==="expert"` par défaut). Vrais clics (`Input.dispatchMouseEvent` à des coordonnées calculées via `getBoundingClientRect()` + `scrollIntoView()`) pour la quasi-totalité du parcours, y compris l'ajout de joueurs via les vrais champs de saisie de l'écran Équipes (pas d'injection directe dans `S`). Frappe clavier réelle (`Input.insertText`, caractère par caractère) pour les notes coach de Bilan. `localStorage`/IndexedDB nettoyés avant le passage (`Storage.clearDataForOrigin`), reload réel de la page. Écran d'accès Supabase contourné via `S.authOk=true` après résolution de `checkAuthSession()`. **Réseau bloqué vers `*supabase.co*`** (`Network.setBlockedURLs`) pour garantir qu'aucune donnée de test ne puisse jamais atteindre le vrai projet Supabase de production — cohérent avec la méthode déjà suivie par le QA de ce cycle.

**Dialogues natifs (`window.alert`/`window.confirm`) traités via le vrai protocole CDP**, pas neutralisés côté page : écoute de `Page.javascriptDialogOpening`, réponse via `Page.handleJavaScriptDialog` avec le texte exact du message capturé à chaque fois. Ce choix (plus lourd qu'un simple monkey-patch `window.alert=()=>{}`) a permis de vérifier **mot pour mot** les textes de confirmation critiques de ce cycle (alerte de blocage pénalty de STORY-33, texte quantifié vs non quantifié de STORY-36, confirmation de dirty-state de STORY-35) plutôt que de seulement constater qu'une boîte de dialogue s'est affichée. Un flag `cdp._dialogAccept` permet de tester explicitement les chemins "Annuler" (rejet d'un `confirm`) là où le cycle l'exige (STORY-35 AC14, STORY-36 AC5/AC6/AC8).

Pour le `<select>` GB (scoreboard, filtre Stats, sélecteur de match Bilan), le geste utilisateur a été simulé par l'équivalent fonctionnel exact d'une sélection réelle : `select.value=...` puis `dispatchEvent(new Event('change',{bubbles:true}))` — c'est strictement le binding réel du handler `onchange` qui est exercé.

Pour le correctif P0 de STORY-36, le scénario "match réellement en cours avec souscription Realtime active" a été reproduit fidèlement : `S.currentMatchId` réglé sur un identifiant réaliste puis `subscribeMatchEvents(id)` **réellement appelé** (créant un vrai objet `realtimeChannel` côté client `supabase-js`, indépendant du succès de la connexion réseau — celle-ci est de toute façon bloquée par la protection prod ci-dessus), avant de déclencher le raccourci et de vérifier que `S.currentMatchId` **et** `realtimeChannel` (variable de module top-level, lisible directement via `Runtime.evaluate` comme n'importe quel `let`/`const` de script classique) sont bien tous deux redevenus `null` après coup.

## Anecdotes méthodologiques (défauts du script de test, pas de l'application)

1. **Reprise d'une tentative interrompue.** Une première tentative de ce passage avait été interrompue par une limite de session avant de produire le moindre document — mais elle avait laissé une instance Chrome headless orpheline tournant encore (port 9931, profil dans le dossier du projet lui-même plutôt que dans le scratchpad) ainsi que plusieurs scripts de test déjà écrits et validés (`rg79_01_setup.js`, `rg79_02_core.js`) pour l'écran Équipes et le workflow Expert complet. L'instance orpheline a été arrêtée et son profil supprimé avant de démarrer une instance neuve dédiée à ce passage ; les deux scripts déjà écrits ont été relus intégralement, confirmés conformes au code actuellement en place (aucune dérive de ligne ni de sélecteur), puis réutilisés tels quels comme fondation du passage plutôt que réécrits inutilement.
2. **Un `showToast(msg, true)` (bandeau d'alerte 4 secondes, `position:fixed;top:20px;z-index:9999`) peut visuellement recouvrir la barre de navigation du header.** Après le test de revalidation du tireur (STORY-33 P1-4), le toast "Le tireur désigné n'est plus disponible…" reste affiché 4000ms. Un clic sur `[data-v="setup"]` déclenché trop tôt après (150ms) a atterri sur le toast plutôt que sur le bouton de nav réel — la coordonnée cliquée était correcte, mais un élément à z-index supérieur interceptait le clic. `clickEl()` ne lève pas d'exception dans ce cas (l'élément ciblé existait bel et bien au moment du calcul du rect), donnant un faux "succès" ; c'est l'assertion suivante (tentative de clic sur un sélecteur propre à l'écran Équipes, introuvable puisque toujours sur Match) qui a révélé le problème. Corrigé par une fonction d'attente explicite de disparition du toast avant tout clic de navigation proche du haut de l'écran, plus un principe général adopté pour la suite du passage : journaliser chaque résultat intermédiaire immédiatement (`console.log`) plutôt qu'en fin de script, pour ne jamais perdre les vérifications déjà réussies si une étape de nettoyage ultérieure échoue.
3. **`#settings-btn` est un simple toggle (`S.settingsOpen=!S.settingsOpen`), pas un "ouvrir".** Un script qui ré-ouvre le panneau Réglages sans vérifier s'il était resté ouvert d'une étape précédente peut le refermer par erreur, faisant échouer le clic suivant sur un bouton qui n'existe plus dans le DOM (`#new-btn`, `#save-match-btn`). Corrigé en fermant systématiquement le panneau (`#close-settings`) avant chaque section qui le rouvre.
4. **`document.querySelectorAll('table tr')` ne trouve rien sur l'onglet Stats → Joueurs** — pas un défaut de l'app : `renderStatPlayers()` n'utilise jamais de balise `<table>`, seulement des `<div>` empilées (`[data-player-detail]` par ligne joueur). Vérifié directement par lecture de `document.querySelectorAll('[data-player-detail]')`, qui retrouve bien les 4 lignes joueur attendues avec les bonnes statistiques (dont un "50%%" dans le `textContent` brut — pas un double pourcentage affiché à l'écran, simplement la concaténation sans espace de deux `<div>` adjacentes distinctes : la valeur "50%" et, juste en dessous, l'étiquette "%" du bloc suivant — comportement CSS existant, inchangé par ce cycle, non testable par une capture de `textContent` brut sans faux positif).

Aucun des quatre points ne concerne un défaut de `app.js` — uniquement la fiabilité du harnais de test. Une fois ces points identifiés, le passage complet est reproductible et propre : zéro exception JS non anticipée sur l'ensemble des ~200 appels `Runtime.evaluate` du passage final (hors les quelques appels volontairement enveloppés dans un `try/catch` pour vérifier qu'un tap orphelin ou une revalidation refusée ne lève justement **pas** d'exception).

## Point central confirmé
