# Regression Guardian — passage avant mise en production v72

## Changement de cette version
STORY-27 : suppression réelle d'un match sur Supabase (ligne `matches` + tous ses `match_events`) quand ce match est supprimé depuis l'historique local (écran Matchs, bouton 🗑). Avant cette story, `[data-del-match]` ne supprimait que la copie locale (IndexedDB) — la copie Supabase restait indéfiniment, contrairement à ce que l'app laissait penser à l'utilisateur.

Diff `app.js` (+15/-0 lignes, cf. `docs/code-review/STORY-27.md`) :
- `saveMatch()` : ajout du champ `supabaseMatchId:S.currentMatchId||null` sur l'objet match persisté (l.1350).
- Nouvelle fonction `deleteSupabaseMatch(matchId)` (l.1371-1378) : supprime `match_events` avant `matches` (pas de `ON DELETE CASCADE` dans le schéma), best-effort (`try/catch` sans retry).
- Handler `[data-del-match]` (l.3890-3902) : après suppression locale réussie, appelle `deleteSupabaseMatch(m.supabaseMatchId)` en fire-and-forget (non `await`é) si ce champ existe ; texte de confirmation enrichi (caractère définitif + portée multi-appareil, correctif du point Mineur remonté par le Security Auditor).
- `sw.js` bumpé v71→v72.

Code Review **APPROUVÉ** (`docs/code-review/STORY-27.md`), Security Auditor feu vert sans Critique ni Majeur nouveau (`docs/security/story-27-suppression-supabase.md`), QA **PASSED** (`docs/qa/QA-27-suppression-supabase.md`).

## Pourquoi une passe complète, pas juste un test de fumée
Surface de code réduite (une fonction, un champ, un handler modifié), mais qui touche :
1. Une action **irréversible** sur des données **partagées** (Supabase, compte unique multi-appareil) ;
2. Le flux de **sauvegarde/suppression de match**, déjà identifié comme point sensible dans ce projet (STORY-14, mode lecteur).

Le QA n'a pas pu tester la suppression Supabase réelle (pas de compte authentifié disponible en environnement de test, échecs 401 attendus) — sa validation porte sur la logique (garde-fous, ordre des opérations). Ma passe reprend donc le parcours critique complet du projet, avec une attention particulière portée exactement là où le Developer, le Code Reviewer et le QA ont indiqué le risque : que sauvegarder puis supprimer un match ne casse rien d'autre — l'historique local, l'export/import CSV, ni le chargement d'un ancien match `[data-load-match]` (notamment ceux sauvegardés **avant** ce correctif, donc sans `supabaseMatchId`).

## Méthode
Tests réels via CDP (Chrome headless dédié `--headless=new`, profil temporaire isolé, port **9900** — libre et distinct des ports déjà utilisés cette session : 9371, 9455, 9512, 9600, 9640, 9641, 9700, 9812, 9713), viewport 1180×900 (iPad-like). Vrais clics (`Input.dispatchMouseEvent` sur coordonnées calculées via `getBoundingClientRect()`, avec `scrollIntoView()` avant chaque clic) pour toutes les interactions déterminantes du parcours ; quelques appels directs ciblés pour les vérifications de logique de la nouvelle capacité de suppression Supabase (même limite que le QA : pas de vrai compte Supabase authentifié en environnement de test, donc les tentatives réseau de `deleteSupabaseMatch` échouent en pratique — la vérification porte sur le caractère non-bloquant et l'absence d'exception, pas sur la confirmation d'une vraie ligne supprimée côté serveur). Écran d'accès Supabase contourné via `S.authOk=true` avec double ré-assertion défensive (course avec `checkAuthSession()`, même précaution que les passages précédents). `localStorage` nettoyé avant le passage, IndexedDB vidée pour repartir d'une baseline propre et reproductible, reload réel de la page.

Ajout de joueurs sur l'écran Équipes fait par assignation directe de `S.home.players`/`S.away.players` plutôt que par le bouton "+ Ajouter" (qui ouvre un `window.prompt()` natif, hors du périmètre à risque de ce cycle — non touché par STORY-27) — choix délibéré pour concentrer le temps de test sur la zone à risque réelle.

## Anecdotes méthodologiques (défauts du script de test, pas de l'application)
Comme documenté dans `docs/regression/v70.md` et `v71.md`, plusieurs itérations ont été nécessaires pour fiabiliser le script — aucune n'a révélé de défaut dans `app.js` :
1. **`#ap-court-svg` inexistant dans le DOM rendu.** Le binding `document.getElementById("ap-court-svg")` existe bien dans `app.js` (l.3799) mais aucun élément du rendu ne porte cet id — le vrai point de clic pour la position de tir est `[data-court-position]` (div plein cadre, coordonnées en pourcentage 0-100 calculées directement depuis `getBoundingClientRect()` de ce div, pas depuis le `viewBox` SVG 350×208). Ce binding mort semble être un reliquat d'une itération antérieure du terrain (probablement antérieur à STORY-22, refonte SVG) ; il n'est pas touché par STORY-27 et n'entraîne aucun effet observable (l'élément visé n'existe simplement jamais, `apCourtSvg` reste `null`, la ligne 3800 `if(apCourtSvg)` ne s'exécute jamais). Sans conséquence fonctionnelle car `[data-court-position]` fait le travail. Corrigé côté script une fois identifié par lecture de `app.js`.
2. **Sanction 2min/Carton : mauvais point d'entrée.** Le bouton de la barre d'actions `[data-act="TWO_MIN"]` ne fait que sélectionner l'action (`selectAction()`) — il n'ouvre aucun overlay de sélection joueur. Le vrai point d'entrée du flux 2min/carton est le badge du scoreboard `[data-badge="home|TWO_MIN"]` / `[data-badge="away|TWO_MIN"]`, qui ouvre `#ps-overlay` avec les `[data-pick-player]`. Corrigé une fois le bon binding identifié par lecture de `app.js` (l.3855-3864).
3. **Boutons Sauvegarder/Nouveau match dans le panneau Réglages, fermé par défaut.** `#save-match-btn` et `#new-btn` ne sont rendus dans le DOM que si `S.settingsOpen===true` (l.1751). Le premier passage cliquait directement sur ces sélecteurs sans avoir ouvert `#settings-btn` au préalable — `clickSelector` retournait "not found" silencieusement, ce qui a fait échouer en cascade la vérification de sauvegarde (`supabaseMatchId` jamais persisté puisque `saveMatch()` n'était jamais appelée) et celle de l'historique (seul le match "legacy" injecté directement apparaissait). Corrigé en ouvrant `#settings-btn` avant chaque clic sur un bouton de ce panneau.
4. **PD : le vivier de passeurs exclut le buteur par conception.** `renderPdSelect()` (l.2036) filtre explicitement le buteur de la liste des passeurs éligibles. Avec un effectif synthétique réduit à 2 joueurs par équipe pour aller vite (un joueur de champ + un gardien), le seul passeur éligible après un but du joueur de champ était... le gardien. Le premier passage du script visait `[data-pick-pd]` sur l'id du buteur (qui n'existe donc jamais dans cette liste), d'où un overlay resté ouvert et un assist jamais assigné. Corrigé en ciblant l'autre joueur de l'effectif — comportement de filtrage confirmé conforme au code, pas un bug.
5. **Clic sur un élément dupliqué et masqué (`#t-toggle`).** Les layouts mobile et desktop du bandeau chrono rendent chacun un élément `id="t-toggle"` simultanément dans le DOM (l.1784 et l.1910), un seul étant visible selon le media query CSS actif. `document.getElementById`/`querySelector` renvoie systématiquement le premier du DOM, qui n'est pas forcément le visible : son `getBoundingClientRect()` est alors entièrement à zéro, et le clic atterrissait donc au point (0,0) de la page sans effet. Corrigé en généralisant le script pour toujours choisir, parmi les éléments correspondant à un sélecteur, le premier dont le rectangle a une taille non nulle — sans quoi le clic échoue explicitement plutôt que de silencieusement rater sa cible. Ce doublon d'id (`#t-toggle`, `#per-btn`, `#gk-timeline-btn`, etc., visibles dans le grep des deux layouts) est un fait préexistant de l'architecture responsive du projet, pas une régression de STORY-27 — il n'entraîne aucun bug applicatif réel (un seul des deux `id="t-toggle"` est jamais cliquable par un vrai doigt/souris puisque l'autre est masqué visuellement), seulement un piège pour un script CDP qui clique par sélecteur plutôt que par position visuelle réelle.

Aucun de ces cinq points ne concerne un défaut de `app.js` — uniquement la fiabilité du harnais de test. Une fois corrigés, le passage complet est reproductible et propre, zéro exception JS et zéro `exceptionDetails` remonté par CDP sur l'ensemble des ~50 appels `Runtime.evaluate` de la session.

## Point central confirmé
Le scénario redouté — qu'ajouter une suppression Supabase casse la suppression locale, l'historique, ou les exports/imports existants — **ne se produit pas** :
- Un match sauvegardé **avant** ce correctif (sans `supabaseMatchId`) se charge, s'affiche et se supprime exactement comme avant STORY-27 — `deleteSupabaseMatch` n'est simplement jamais invoquée pour lui (`m?.supabaseMatchId` falsy), confirmé par test réel et pas seulement par lecture de code.
- Un match sauvegardé **après** ce correctif obtient bien un `supabaseMatchId` correct, et sa suppression locale est instantanée (la tentative Supabase, fire-and-forget, n'a jamais retardé la mise à jour de l'écran — confirmé par une durée mesurée sous la seconde et un `R()` déjà effectué avant même la résolution de la promesse réseau).
- L'export et l'import CSV ignorent totalement le nouveau champ (ni exposé dans le fichier produit, ni requis à l'import) — un cycle export→import réel via un vrai `File`+événement `change` sur l'input du code de production fonctionne sans erreur.
- Aucun des ~13 autres points du parcours critique (workflow BUT Expert, PD, chrono, TM, mi-temps, sanction 2min, gardien, undo, sync sortante/entrante, mode Simple/Expert, mode lecteur) n'est affecté par ce diff de 15 lignes.

## Verdict
**RAS** — aucune régression détectée.

STORY-27 (suppression réelle d'un match sur Supabase) tient ses promesses : suppression best-effort, jamais bloquante, sans impact sur l'historique local, l'export/import CSV, ni le chargement d'anciens matchs dépourvus du nouveau champ. L'ensemble du parcours critique du projet reste inchangé.

Feu vert pour la mise en production v72.
