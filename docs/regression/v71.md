# Regression Guardian — passage avant mise en production v71

## Changement de cette version
STORY-15 : indicateur discret de statut de synchronisation (✓ sync / ↻ envoi… / ⚠ hors-ligne) dans le bandeau haut de l'écran Match. Historique de la story : 1ère passe de code review **REJETÉE** (un `R()` complet était déclenché depuis le `finally` de `flushOutbox()`, le listener `online`, et le nouveau listener `offline` — donc à chaque tick du `setInterval(15000)` qui tourne en continu pendant tout un match, avec un risque concret de perte de focus/de saisie sur un champ texte ailleurs dans l'app). Corrigée en remplaçant ces trois points d'appel (plus `dequeueEventSync()`) par un patch DOM ciblé `patchSyncIndicator()`, sur le modèle déjà en place de `renderTimer()`. Code review **APPROUVÉ** après correctif (`docs/code-review/STORY-15.md`), QA **PASSED** (`docs/qa/QA-15-16-17.md`).

STORY-16 (audit de clarté d'interface pour un aidant occasionnel) et STORY-17 (documentation de clonage) n'ont livré aucun code — hors du périmètre d'une passe de non-régression, écartées ici conformément au mandat.

## Pourquoi une passe complète, pas juste un test de fumée
Seule STORY-15 touche du code, mais elle touche exactement les points sensibles décrits par le Code Reviewer et le QA : `flushOutbox()` (appelée après chaque événement saisi **et** toutes les 15 secondes en continu pendant toute la durée d'un match via `setInterval`), `dequeueEventSync()` (undo), et les listeners réseau `online`/`offline`. Un changement petit en surface mais qui s'exécute en continu pendant un match réel justifie une vérification approfondie du parcours de saisie complet — pas seulement de la nouvelle feature elle-même (déjà couverte par le QA) — avec une attention particulière portée sur la préservation du focus d'un champ texte en cours de saisie pendant que ce cycle périodique tourne.

## Méthode
Tests réels via CDP (Chrome headless dédié `--headless=new`, profil temporaire isolé, port **9812** — distinct des ports déjà utilisés dans cette session), viewport élargi à 1180×900 (iPad-like, le vrai appareil cible du projet) pour éviter les faux clics hors-écran en headless. Vrais clics (`Input.dispatchMouseEvent` sur coordonnées calculées via `getBoundingClientRect()`, avec `scrollIntoView()` systématique avant chaque clic) pour toutes les interactions déterminantes du parcours ; quelques appels directs ciblés pour des vérifications d'état non ambiguës (`mergeRemoteEvent()`, lecture de l'outbox). Écran d'accès Supabase contourné via `S.authOk=true` avec ré-assertion défensive contre la course avec `checkAuthSession()` (même précaution documentée par le QA et par v70). `localStorage` nettoyé avant le passage (`hb2_teams`, `hb2_readonly` retirés, `hb2_mode` forcé à `"expert"`), reload réel de la page pour repartir d'un état neuf et reproductible.

Le test central de ce cycle — préservation du focus/de la valeur d'un champ texte pendant le cycle périodique de sync — a été fait en **conditions réelles** : le `setInterval(flushOutbox, 15000)` natif de l'app n'a jamais été appelé manuellement ni raccourci ; le script a réellement attendu ~15s à deux reprises (plus un dispatch réel des événements DOM `online`/`offline`) pendant qu'un champ était activement focus avec une frappe non validée, de l'outbox local réellement alimenté (`outboxPut()` direct + événements réels créés pendant le match) pour que chaque cycle de `flushOutbox()` ait effectivement du travail à faire (`flushInProgress`, upsert, etc.), pas un cycle no-op.

## Anecdotes méthodologiques (défauts du script de test, pas de l'application)
Comme documenté dans `docs/regression/v70.md`, plusieurs itérations ont été nécessaires pour fiabiliser le script de test lui-même — aucune n'a révélé de défaut dans `app.js` :
1. **Sélecteur de joueur sur le terrain erroné** : le script utilisait un sélecteur générique (`[data-pid]`) qui ne correspond à aucun attribut réel du DOM. Lecture du code : les joueurs sur le terrain utilisent `data-ap-player` (panneau d'action principal) ou `data-pick-pd`/`data-pick-player` (overlays dédiés PD et 2min/Carton rouge, deux markups distincts). Corrigé une fois les bons attributs identifiés par lecture de `app.js`.
2. **Overlay laissé ouvert bloque les clics suivants** : après correction du point 1, cliquer sur le bouton PD ouvrait bien l'overlay plein écran `#pd-overlay` (`.ps-overlay`), mais le script ne le refermait pas avant de continuer — `document.elementFromPoint()` a confirmé que les clics suivants (chrono, sanction 2min, annuler) atterrissaient sur l'overlay et non sur les boutons visés. Corrigé en assignant systématiquement l'assist (ou en cliquant "Annuler") avant de poursuivre. Même mécanisme, une fois compris, expliquait aussi l'échec initial du test de sanction 2min (overlay `#ps-overlay` non refermé faute du bon sélecteur de joueur).
3. **`window.alert()` natif bloquant sous CDP** : `saveMatch()` appelle `safeAlert()`, qui appelle `window.alert()` en environnement réel navigateur (fallback documenté dans `app.js`, prévu pour la compatibilité viewer Claude HTML). Sous CDP, une boîte de dialogue JS native suspend l'exécution du renderer jusqu'à ce qu'elle soit explicitement acquittée (`Page.handleJavaScriptDialog`) — sans ce handler, l'appel a bloqué le script indéfiniment. Corrigé en ajoutant un auto-acquittement des événements `Page.javascriptDialogOpening`.
4. Un test antérieur du même script a également buté sur des onglets Chrome orphelins (processus de script tueur avant leur fermeture propre), chacun gardant une connexion IndexedDB ouverte sur le même profil — fermés explicitement (`/json/close/{id}`) avant de relancer, plus un garde-fou watchdog ajouté au script (fermeture forcée de l'onglet si le run dépasse 120s) pour qu'un futur blocage ne laisse plus jamais fuiter un onglet.

Aucun de ces quatre points ne concerne `app.js` — uniquement la fiabilité du harnais de test. Une fois corrigés, le passage complet est **reproductible et propre** (voir résultat ci-dessous), avec zéro exception JS et zéro erreur console sur l'ensemble de la session.

## Point central confirmé
Le scénario exact qui avait motivé le rejet de la 1ère passe de code review — perte de focus/de saisie sur un champ texte pendant que `flushOutbox()` tourne toutes les 15s en continu — **ne se reproduit plus**. Testé en conditions réelles (intervalle natif, pas d'appel manuel raccourci) sur deux champs différents (`team-name-input` sur l'écran Équipes, `coach-notes` sur Stats → Analyse), à travers deux cycles complets de 15s plus un dispatch réel des événements `online`/`offline`, avec de l'activité réelle dans l'outbox à chaque cycle (`syncPendingCount` non nul, jusqu'à 22 lignes en attente pendant le test). Le patch DOM ciblé (`patchSyncIndicator()`) ne touche jamais que `.sync-indicator`, exactement comme documenté par le Code Reviewer et le QA.

## Verdict
**RAS** — aucune régression détectée. Le correctif de STORY-15 (patch DOM ciblé au lieu d'un `R()` complet) tient sa promesse : le cycle périodique de synchronisation ne perturbe plus jamais la saisie en cours ailleurs dans l'app, y compris en conditions réelles sur plusieurs cycles consécutifs. L'ensemble du parcours critique — workflow BUT Expert, mode Simple, chrono/mi-temps, TM, sanctions, gardien, PD, annuler un événement, sauvegarde/nouveau match, écran Équipes avec saisie de texte, sync sortante/entrante, mode lecteur — se comporte à l'identique d'avant STORY-15.

Feu vert pour la mise en production v71.
